# Guía del proyecto

- El proyecto usa C# con .NET 10, Worker Service/Generic Host y EF Core 10 con SQL Server; conserva estas tecnologías salvo decisión explícita del usuario.
- La ejecución de cliente se distribuye como contenedor Linux con Docker Compose. No agregues integración nativa con Windows Service/systemd/launchd salvo requerimiento explícito; el SO anfitrión necesita Docker Desktop (Windows/macOS) o Docker Engine (Linux), no el runtime .NET.
- En Development, `ConnectionStrings:FEL` se obtiene de .NET User Secrets y el arranque aplica migraciones. No pongas cadenas de conexión en `appsettings*.json`, Compose ni otros archivos versionados. Consulta el README para comandos de configuración y migración.
- Cada fila `SaeCompany` representa una base SAE; deriva su nombre desde la versión y número de empresa, sin persistir credenciales por empresa. El servidor/credenciales se comparten desde secretos externos a FEL.
- `dbo.Documents` vive en FEL y referencia `SaeCompanies`; el trigger `FEL_EMITIDAS` vive en las bases SAE y queda fuera de las migraciones de FEL. Conserva los nombres exactos de estado (`Pending`, `Processing`, `Signed`, `Delivered`, `Rejected`, `Failed`) y la clave única CompanyId/LocationId/DocumentType/InternalId.
- Guarda Request/Response JSON o XML en columnas de texto `nvarchar(max)` y el PDF como bytes en `varbinary(max)`; estos campos son opcionales al ingresar por trigger y no se deben forzar a estar completos antes del procesamiento.
- El JSON provisional usa `Document` con `Issuer`, `Receiver`, `Items` y `FreeFields`; el contrato final fiscal aún no está acordado. Trata Request/Response como datos sensibles: no incluirlos en logs y mantener secretos fuera del payload. El payload va al certificador, nunca al API de la nube; usa HTTPS y no añadas criptografía de payload ad hoc.
- El contrato del API que este worker consume está en `api-architecture.md` y es la referencia obligatoria. Consume solo cuatro endpoints: `POST /agent/handshake`, `POST /agent/token/refresh`, `POST /agent/heartbeat` y `POST /agent/documents/status`. No inventes rutas, CRUD ni endpoints de configuración, y no agregues sockets crudos, WebSocket ni SignalR: el API no los expone y los comandos llegan únicamente en la respuesta del latido. Usa un `HttpClient` tipado con conexión reutilizada, backoff y respeto de `Retry-After`; 401 implica refrescar el token y 403 implica licencia inválida.
- Al API se envían solo metadatos: nunca `Request`, `Response` ni `Pdf`. El lote va de 1 a 100 documentos y la `IdempotencyKey` se deriva de la clave natural de la cola, `CompanyId-LocationId-DocumentType-InternalId`. Mantén los nombres de estado locales y traduce al enum del API (`Pending`, `Processing`, `Certified`, `Error`, `Retrying`) solo en el borde del cliente HTTP. `branchId` se envía `null` mientras no exista mapeo acordado para `LocationId`. Los comandos se confirman con `acknowledgedCommandIds`; antes de atender `ResendDocument` consulta al certificador si el documento ya se certificó.
- Hay una credencial de agente por empresa SAE. Hoy el `agentId` y el secreto se leen de configuración (User Secrets, variables de entorno o Docker secrets en `/run/secrets`), indexados por el `Id` de la fila de `dbo.SaeCompanies`; persistir en FEL el `agentId` y los GUID de tenant/empresa del API sigue pendiente. El secreto nunca se guarda en FEL, en el repositorio ni en la imagen. El refresh token se persiste **cifrado con Data Protection** en el almacén de tokens (`FelApi:TokenStorePath`, un volumen montado), nunca en FEL ni en claro; si no se puede descifrar se descarta y el worker rehace handshake. Ni el secreto ni los tokens se registran en logs.
- La autorización de envío es deny-by-default: solo una empresa configurada con licencia confirmada puede autorizar envío. El API es la fuente autoritativa y entrega `licenseState` (`Active`, `Grace`, `Suspended`) en handshake y refresh: aplícalo con `ApplyLicenseStatusFromCloud`, permite envío en `Active` y `Grace`, deniégalo en `Suspended` y no calcules expiración ni períodos de gracia en el worker. Sin sincronización la empresa sigue denegada y no se habilita `IsLicensed` a mano. No implementes transiciones de documentos ligadas a respuestas del certificador hasta que exista su contrato.
- La lógica de todos los certificadores y países vive en el worker, organizada por certificador y país con su formato y ambiente; el API nunca llama al certificador. Mientras el API no exponga la configuración y credenciales por empresa, el worker no certifica: no crees tablas, catálogos locales ni plantillas de certificador por adelantado, y no persistas credenciales de certificador ni P12 en FEL, el repositorio o la imagen.
- Guarda `CustomerSql` y `ProductSql` una sola vez en `dbo.SaeCommonQueries` por empresa/versión; son compartidas por todos los tipos. Mantén `DocumentSql`, `IssuerSql`, `ItemsSql` y `FreeFieldsSql` en `dbo.SaeDocumentQueries` por empresa/versión/tipo. El origen y la forma de `PAR_FACT` pueden cambiar entre tipos, mientras el lookup del producto usa la consulta común a `INVE`. Mantén tipados y parametrizados `@InternalId`, `@InternalNumber`, `@InternalSerial`, `@LocationId`, `@DocumentType` y `@ProductCode`; no interpolar valores. Sigue el contrato del README: columna `Json` para objetos y partidas, alias `ProductCode` en cada partida y columnas `Name`/`Value` para campos libres. No inventes plantillas de producción sin validar el DDL SAE del cliente.
- Las plantillas SQL se ejecutan como texto y el Worker no valida que sean solo lectura. Mantén la cuenta usada para acceder a cada base SAE con permisos mínimos de solo lectura; restringe quién puede editar ambas tablas de consulta. No escribas en SAE fuera de la operación autorizada de actualización de clientes.
- El lector SAE genera el JSON provisional para un documento individual, pero no reserva ni procesa automáticamente la cola, no persiste por sí solo los cambios del `Document` ni envía al API. Conserva explícito este límite hasta implementar el procesamiento end-to-end.
- Mantén el alcance de cada cambio acotado. Siguen pendientes el procesamiento de la cola, el cliente HTTP del API, los providers por certificador y país, el latido y la sincronización de licencia, ya con contrato definido en `api-architecture.md`; consulta el README para el propósito y límites del sistema.
- Nunca agregues secretos al código, a archivos versionados ni a logs: esto incluye credenciales SAE/FEL, credenciales de otras empresas, llaves de certificador y certificados P12. No registres cadenas de conexión completas.
- Mantén el `Dockerfile` multi-stage y no copies archivos locales de secretos a imágenes; verifica que el contenedor pueda detenerse limpiamente y que la configuración de Docker no publique puertos innecesarios.
- Mantén aislada la configuración de cada empresa SAE. No escribas en SAE salvo para la operación autorizada de actualización de clientes cuando `puedeActualizarClientes` esté habilitado.
- Antes de agregar nuevas dependencias o comportamiento, verifica que sean necesarios para el requerimiento. Ejecuta `dotnet build WisFel.Worker.slnx` para validar cambios de código.
