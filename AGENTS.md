# Guía del proyecto

- El proyecto usa C# con .NET 10, Worker Service/Generic Host y EF Core 10 con SQL Server; conserva estas tecnologías salvo decisión explícita del usuario.
- La ejecución de cliente se distribuye como contenedor Linux con Docker Compose. No agregues integración nativa con Windows Service/systemd/launchd salvo requerimiento explícito; el SO anfitrión necesita Docker Desktop (Windows/macOS) o Docker Engine (Linux), no el runtime .NET.
- En Development, `ConnectionStrings:FEL` se obtiene de .NET User Secrets y el arranque aplica migraciones. No pongas cadenas de conexión en `appsettings*.json`, Compose ni otros archivos versionados. Consulta el README para comandos de configuración y migración.
- Cada fila `SaeCompany` representa una base SAE; deriva su nombre desde la versión y número de empresa, sin persistir credenciales por empresa. El servidor/credenciales se comparten desde secretos externos a FEL.
- `dbo.Documents` vive en FEL y referencia `SaeCompanies`; el trigger `FEL_EMITIDAS` vive en las bases SAE y queda fuera de las migraciones de FEL. Conserva los nombres exactos de estado (`Pending`, `Processing`, `Signed`, `Delivered`, `Rejected`, `Failed`) y la clave única CompanyId/LocationId/DocumentType/InternalId.
- Guarda Request/Response JSON o XML en columnas de texto `nvarchar(max)` y el PDF como bytes en `varbinary(max)`; estos campos son opcionales al ingresar por trigger y no se deben forzar a estar completos antes del procesamiento.
- El JSON provisional usa `Document` con `Issuer`, `Receiver`, `Items` y `FreeFields`; el contrato final fiscal aún no está acordado. Trata Request/Response como datos sensibles: no incluirlos en logs y mantener secretos fuera del payload. Para la API futura usar HTTPS y autenticación acordada; no añadir criptografía de payload ad hoc.
- La autorización de envío es deny-by-default: solo una empresa configurada con licencia confirmada puede autorizar envío. La nube será fuente autoritativa; no inventes expiración/períodos de gracia ni implementes transiciones de documentos ligadas a respuestas API hasta que exista su contrato.
- Las consultas SAE se almacenan en `dbo.SaeDocumentQueries` por empresa, versión y tipo documental. Su SQL es configurable para soportar personalizaciones por cliente; no dupliques procedimientos ni hardcodees nombres de tablas con sufijo. Mantén parámetros `@InternalId`, `@InternalNumber`, `@InternalSerial`, `@LocationId`, `@DocumentType` tipados y evita interpolarlos. Los resultados deben respetar el contrato descrito en README (`Json` para objetos/partidas y `Name`/`Value` para campos libres). No inventes plantillas de producción sin validar el DDL SAE del cliente.
- Las plantillas SQL se ejecutan como texto y el Worker no valida que sean solo lectura. Mantén la cuenta usada para acceder a cada base SAE con permisos mínimos de solo lectura; restringe también quién puede editar `SaeDocumentQueries`. No escribas en SAE fuera de la operación autorizada de actualización de clientes.
- El lector SAE genera el JSON provisional para un documento individual, pero no reserva ni procesa automáticamente la cola, no persiste por sí solo los cambios del `Document` ni envía al API. Conserva explícito este límite hasta implementar el procesamiento end-to-end.
- Mantén el alcance de cada cambio acotado. El procesamiento de cola/envío al API, sincronización cloud de licencias, comandos y heartbeat siguen pendientes; consulta el README para el propósito y límites del sistema.
- Nunca agregues secretos al código, a archivos versionados ni a logs: esto incluye credenciales SAE/FEL, credenciales de otras empresas, llaves de certificador y certificados P12. No registres cadenas de conexión completas.
- Mantén el `Dockerfile` multi-stage y no copies archivos locales de secretos a imágenes; verifica que el contenedor pueda detenerse limpiamente y que la configuración de Docker no publique puertos innecesarios.
- Mantén aislada la configuración de cada empresa SAE. No escribas en SAE salvo para la operación autorizada de actualización de clientes cuando `puedeActualizarClientes` esté habilitado.
- Antes de agregar nuevas dependencias o comportamiento, verifica que sean necesarios para el requerimiento. Ejecuta `dotnet build WisFel.Worker.slnx` para validar cambios de código.
